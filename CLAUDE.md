# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

**Never commit directly to `main`.** Always create a branch first, then merge it (see the `work-on-issue` skill). Every branch is named `<type>/<issue>-<description>` and needs a GitHub issue. `.githooks/pre-commit` refuses commits on `main` and on branches without an issue number; enable it once with `git config core.hooksPath .githooks`.

CV Builder: a React 19 + TypeScript + Vite app (MUI, Redux Toolkit) with a workspace — rail, live A4 preview and inspector — exportable to PDF, plus a small local Fastify server that stores the data as JSON files. The data model (version 0.2): **vault** (all facts) + **templates** (how a CV looks) + **jobs** (one target each: uses a template, decides what to show) + **applications** (frozen copy of what was sent). See "Templates and jobs" below. GitHub issues hold the roadmap and history (#28-#49 first phases, #165-#172 templates and jobs).

## Layout

One package, three folders in `src/`:

- `src/web` — the React app (components, hooks, pages, Redux store, styles). Entry: `src/web/main.tsx`.
- `src/server` — the local API (Node, Fastify). Entry: `src/server/main.ts`.
- `src/shared` — code both sides import: the `runtypes` schemas (`shared/custom-types`) and the pure vault logic (`shared/vault`: migration, file format, helpers). Keep it free of React, Redux and Node APIs.

## Commands

Package manager is **pnpm**.

- `pnpm dev` — web (Vite, :5173) and server (:3001) together; Vite proxies `/api` to the server. `pnpm dev:web` / `pnpm dev:server` run one of them; `pnpm server` runs the server once, without watching. `PORT`, `DATA_DIR` (default `./data`) and `WEB_URL` (default `http://localhost:5173`, must be this machine) configure the server. PDF export needs Chromium once: `pnpm exec playwright install chromium` (downloads ~110 MB to the Playwright cache, not the repo) and the web app running at `WEB_URL`.
- `pnpm build` — `tsc -b && vite build`
- `pnpm test` — Vitest (once); `pnpm test:watch`. Single file: `pnpm exec vitest run src/path/file.test.ts`. Tests live next to the code as `*.test.ts(x)`. Default environment is node; component tests start with `// @vitest-environment jsdom` and use Testing Library (see `pages/editor-page/editors.test.tsx`). Use Node 24 (`nvm use 24`; CI uses 24): jsdom 31 and eslint-plugin-jsdoc 65 need Node 22.22+ or 24.15+. **Held-back packages (#154):** `eslint`/`@eslint/js` stay on v9 because `eslint-plugin-import` and `eslint-plugin-react` do not support ESLint 10 yet; `eslint-plugin-unicorn` stays on v65 (66+ needs ESLint 10); `typescript` is on 6.0 because typescript-eslint supports `<6.1` (TypeScript 7 is the native port); `@types/node` follows the Node 24 runtime. Re-check with `pnpm outdated` when those plugins release. MUI is v9 (system props go in `sx`, `Grid` has no `direction="column"`, icons are `*Outlined`), Vite 8.
- `pnpm test:e2e` — real-browser tests in `src/e2e/*.e2e.ts` (separate Vitest config, not part of `pnpm test`): they start the API on a temp data folder, Vite and Chromium; `pdf.e2e.ts` checks PDFs (page count, A4, text layer via `unpdf`, hidden/ordered content) and `editor.e2e.ts` drives the UI (hide an item, keyboard-reorder a section, save, export PDF, reload). Needs `pnpm exec playwright install chromium` once; CI does it. Use these for anything about real layout, which jsdom cannot show (they already caught a page-count rounding bug).
- `pnpm lint:check` — ESLint on `src`, no changes (what CI runs); `pnpm lint` does the same with `--fix`
- `pnpm knip` — dead-code check (unused files, exports, types, dependencies); exits non-zero when something is unused. Config in `knip.json` (entries: tests and e2e; `main.tsx`, `main.ts` and the Vite config come from the plugins). Remove what it reports instead of ignoring it.
- CI (`.github/workflows/ci.yml`) runs build, lint:check, format-check, knip and test on every PR.
- `pnpm format-check` / `pnpm format-fix` — Prettier (`.prettierrc`: `trailingComma: es5`; keep that style)

## Versioning

SemVer, history in `CHANGELOG.md` (Keep a Changelog). The version lives in three places that must be equal: `package.json`, `src/shared/version.ts` (`APP_VERSION`, shown in `GET /api/health` and the tool rail) and the newest released heading in `CHANGELOG.md`; `version.test.ts` fails otherwise. Every user-visible change adds a line under `## [Unreleased]` in the same PR. **Release:** rename Unreleased to `## [x.y.z] - date` (add a fresh empty Unreleased and update the compare links), bump the three places, merge, then `git tag vx.y.z && git push origin vx.y.z` and `gh release create vx.y.z --notes-file` with that section. While the major number is 0 a minor bump may change the saved data format (the migration chain still reads old files).

## Architecture

**Path aliases are mandatory.** ESLint (`no-restricted-imports`) forbids relative imports (`./`, `../`). Use `@components/*`, `@custom-styles/*`, `@hooks/*`, `@pages/*`, `@store/*` (all under `src/web`), `@shared/*`, `@custom-types/*` (`src/shared/custom-types`), `@server/*`, `@fixtures/*`, `@e2e/*` (`src/e2e`) (defined in `tsconfig.json`, resolved by `vite-tsconfig-paths`). The only exceptions are `src/web/main.tsx` (`./index.css`, `./App`), which carry eslint-disable comments. Also use `useAppDispatch`/`useAppSelector` from `@store/store-helper`, never raw `useDispatch`/`useSelector`.

**State (Redux slices in `src/web/store/`):**

- `vault` — the CV facts: `profile`, `links[]` and dynamic `sections[]` (each with `type`, `title`, `items[]`; each item has `fields`, `bullets[]`, `tags`, `shouldShow`). Defined by the `runtypes` schemas in `custom-types/vault-types.ts`. All edits go through the reducers in `store/vault/vault-slice.ts`. Skills reuse the item model: a group is an item (`fields.category`) whose `bullets` are the skills (`text` = name, `rating`).
- `cvData` — only `metaData` and `style` of the current CV file.
- `app` — UI state: page structure (section ids per `fullWidth`/`left`/`right` column; the ids `personalInfo`/`contactInfo` are the header, anything else is a vault section id), column widths, selected editor page, and the `shouldApplyChanges` / `shouldDiscardChanges` / `shouldAddNewItem` flags. `useSyncStructure` (mounted in `App`) keeps the structure consistent with the sections via `reconcileStructure`.
- `jobs` — the templates and jobs (see "Templates and jobs"). `persistence`, `history` and `chat` hold saving, undo and the chat-to-actions mapping.

**Templates and jobs (0.2, #165-#172).** Words: a **template** is how a CV looks (`TemplateSchema`: layout = section placement per column, style, page limit, skill display, auto-fit policy `isAutoFit`/`fitMode`/`fitLimits`); a **job** is one target (`JobSchema`: `templateId`, company/role, `selection` = hidden items/bullets, order, emphasis, wording per bullet and relevance, `tone`, `tailor` record, `tuning` = result of the last auto-fit). Many jobs can share a template, so a change of look reaches all of them; hiding and wording belong to the job and never touch the vault. The word "variant" no longer appears in the interface. **`Variant` (`custom-types/variant-types.ts`) is only the internal resolved view**: `resolveVariant(template, job)` (`shared/variant/template-job.ts`; `splitVariant` is the inverse) gives the one shape that `render`, pagination, auto-fit, the PDF and the application snapshot consume; its `id` is the job id. `render(vault, variant)` (`shared/variant/render.ts`) is the pure function that turns facts + resolved variant into the document to draw (`RenderedSection`s; sections the layout does not place go to the left column; emphasis draws the item's title bold). `Item.shouldShow` in the vault is not used.

- **Store** (`store/jobs/jobs-slice.ts`; state key `jobs`): `templates[]`, `jobs[]`, `activeJobId`. `activeVariantSelector` (alias `selectActiveVariant`) = `resolveVariant(template of the active job, active job)`, memoised (`resolveCached`) so it keeps its identity until that job or template changes; `variantsSelector` does it for every job. Reducers write by owner and take the **job id** (`jobId`, or `id` for rename/delete): layout/style (`setTemplateAppearance`), `setPageLimit`, `setAutoFit`, `setFitLimits`, `setSkillStyle` go to the job's template (`setAutoFit` off and `setFitLimits` drop `tuning` of every job on it); selection, orders, `setTone`, `setTuning`, `renameJob` go to the job. `createJob` and `copyJob` put the new job on an existing template (default: the active job's), `addTemplate`, `renameTemplate`, `deleteTemplate` (refused while a job uses it and for the last one), `setJobTemplate`, `deleteJob` (keeps the template; the last job cannot go), `setActiveJob`, `insertTailoredJob({job, template?})`. `setVariants(Variant[])` (tests, import, print view) splits each variant into `template-<id>` + job; `setTemplatesAndJobs` loads from disk. The active job's template layout/style mirror `app.structure` and `cvData.style`: `activateVariant` loads them into the editor on switching, `useSyncActiveJob` writes edits back to the template. History snapshots `{vault, templates, jobs, activeJobId}`. `app.tool` is `vault|jobs|templates|tailor|chat|ai`.
- **Saving**: `SavedState` = `{vault, templates: id -> text, jobs: id -> text}`; `planSave` lists what changed per kind; `saveToServer` writes templates, then jobs, then deletes jobs, then templates; `loadFromServer` reads `/api/templates` + `/api/jobs`.
- **UI**: top bar `workspace/job-switcher.tsx` ("Switch job", "Template of this job" with the number of jobs on each template, "New job" -> `new-job-dialog.tsx`: name + template, default = the active job's so it SHARES it, "New template…" copies the current look as "Template N"). Rail tool "Templates" (`templates-page.tsx`): every template with its jobs, Create, Duplicate, Rename, "Use for <job>", Delete (disabled while a job uses it or when it is the last, with the reason). `template-scope.tsx` `TemplateScopeNote` ("Changes template 'X', used by N jobs") shows in the page inspector (nothing selected), above the skill display controls, on the Design page; with an item selected the inspector says its controls change only the job. The "Jobs" editor page (`editor-page/sections/editor-jobs.tsx`; redesigned from the artifact `FZ5pmnoy7MabHKDhh5HyRp`) has a closable explainer, the job bar (job, name, New/Duplicate/Delete, template, page limit buttons, auto-fit, fit status chip from `app.fit`) and two tabs (remembered in `localStorage` `cv-builder-jobs-tab`, default Content): **Content** = `job-content.tsx` (sections with a "Show section" switch, items with tick/expand/Highlight/arrows, bullets with wording select; reuses `SortableRow`, `ItemBullets` helpers from `job-section-items.tsx`) and **Sections & layout** = `EditorPageStructure` (layout cards + `SectionPlacement`, whose `SortableItem` has the include checkbox, area select and arrows; the old separate "Page Structure" page was removed). `Job.hiddenSections` (optional list of vault section ids; `setSectionShown`; `render` skips them; copied by `JOB_OPTIONAL_KEYS`) is the job-level "section not included"; layout/order still belong to the template.
- **Server** (`storage/file-cv-storage.ts`): `templates/<id>.json` and `jobs/<id>.json`; routes `GET/PUT/DELETE /api/templates[/:id]` and `/api/jobs[/:id]`, `GET /api/jobs/:id/resolved` (= `resolveVariant`, used by the print page). `DELETE` of a template a job uses answers 409 `in_use`; `PUT` of a job needs an existing template (400 `invalid`). **Old data:** the `/api/variants` routes and their storage methods are gone. While neither `templates/` nor `jobs/` has any entry and `variants/*.json` exist, each readable variant is read as template `template-<variantId>` + job `<variantId>` (`splitVariant`, `createdAt` = file date; a damaged file is skipped and left alone); the first save/delete of a template or job writes them all out, after which the new folders are the truth (a deleted legacy job never comes back). `variants/` is never changed or deleted.
- **Tailoring creates a job** (`shared/ai/apply-proposal.ts` `createTailoredJob(vault, template, baseJob, proposal, decisions, input)` -> `{job, template?, altUpdates}`; `applyProposal` still returns a `Variant`): selection, relevance, tone and `tailor` go to the job; an accepted section order and a page limit that differs belong to the template, so only then a copy "<template> (tailored)" is made, otherwise the job shares the source template. Source template, base job and vault are never changed. The Tailor page has a Template picker, an editable job name (from the advert's job title) and dispatches `insertTailoredJob` + `activateVariant(resolveVariant(...))`. Chat needs no special case: `operationsToActions` writes via the job-id actions and the slice routes them by owner.
- **No lock.** Nothing is locked after sending: an application is a frozen copy, so editing or deleting the template or job later never changes it. Do not add a lock again; to see what was sent, open the application.

**Routing (#198).** Hand-written, no router library (the app has one page shell and a handful of addresses; `react-router` would add a dependency and its own state for little). `shared/routing/routes.ts` is pure: `parseRoute(pathname, search)` / `formatRoute(route)` (inverse) and `legacyRedirect` (old `/?applications...`, `/applications/<id>`, `/?print=<id>` and `/` -> new address). Addresses: `/vault[/<section>[/<item>]]`, `/jobs[/<job>][?view=settings]`, `/templates[/layout|/style]`, `/tailor`, `/chat[/<job>]`, `/settings` (`/ai` is read as the same), `/applications[?q&status&sort&dir]`, `/applications/<id>`, `/print/<job>` (the server's `PdfRenderer` opens it); anything else is `notFound`. `hooks/navigation.ts`: `navigate(route|url, {replace})` (pushState + an event), `useRoute()` (`useSyncExternalStore` over `popstate`), `onAppLinkClick` (plain left click navigates, modifier clicks keep the browser's behaviour; use it with a real `href` on rail items, tree items, tabs) and `useUnappliedDraft(isDirty)` (set by `useVaultDraft` when the draft differs from the store): while an editor holds one, `navigate` and Back ask `window.confirm` first. **The address is the source of truth.** `App` renders by route (`Workspace route` for the tools; the applications pages and the print page are separate and reached by a normal page load, so closing/leaving warns through the existing `beforeunload`). Workspace derives the tool from the route; `hooks/use-route-sync.ts` mirrors it into `app.tool` and clears the canvas selection, and keeps the **active job** in step both ways without a loop: `/jobs/<id>` and `/chat/<id>` activate that job, and when the active job changes by other means (switcher, new job, tailoring, delete) the address follows; whichever changed since the last run wins. `/jobs` and `/chat` without an id get the active job's (replace). `VaultPage` reads section and item from the address and mirrors the section into `app.selectedSectionInEditorPage` for the footer and old editors. `Workspace` shows `NotFound` (`workspace/not-found.tsx`) for an unknown job, vault section or item once the data has loaded (`persistence.status` is not `loading`), and sets `document.title`. Templates: `/templates` (list) and `/templates/<id>/design` (#212, #283: the template the Design page edits; `/templates/design` without an id is filled in with the active job's template by `replace`; an unknown id shows `NotFound`). `app.editedTemplateId` (set by `use-route-sync`, null = the active job's template) is the template that `app.structure`/`cvData.style` mirror: `useSyncActiveJob` loads its look when it changes (before any write, so one template's look never lands in another) and writes edits back with `setTemplateLook({templateId, ...})`; `editedTemplateSelector` and `restore` in `history.ts` follow it too, so undo puts the right look back and `TemplateScopeNote` names it. The templates page has `EditedTemplateSwitcher` and an Edit link on each card; the card clicked on the list is the one the Layout/Style links open. Rail items are `<a>` links, so tests use `getByRole("link")`.

**Item description (#242, first of three).** Experience and education items have a free-text `fields.description` (the generic type already had one; no schema change, no migration), edited in the vault item editor (`fieldSpecsFor`) and drawn by `ItemDescription` (`preview-page/item-description.tsx`: one `data-cv-block` per non-empty line) before the bullets. The bullets are made per job (#243, below); #244 removed the vault bullets.

**Bullets from the description (#243, second of three).** `ItemSelection.generated` (`{id, text}[]`, optional) holds the bullets AI made from an item's `fields.description` for that job; `jobBullets(item, selection)` (`shared/variant/render.ts`) gives the effective bullets (generated when there are some, else the vault's) and `sortBulletsByVariant`/`render` use it, so hide/order/outline/Jobs content work on them like on vault bullets (chat, tailor and hide still see the vault bullets). `generatedBulletsChange` (variant-utils) builds the `setItemSelection` change and drops choices on the replaced bullets. `POST /api/ai/bullets {itemId, mode: make|shorten|rephrase|emphasise, requirements?, focus?, current?}` (`server/ai/generate-bullets.ts`, prompt `generate-bullets.md`, types `custom-types/bullets-types.ts`, task `chat` in the provider chooser) reads the SAVED vault, sends the description + the item's other fields (never the profile; scrubbed like tailoring) and returns `{itemId, bullets: [{text, flags}]}` with `flags` always recomputed with `checkRewrite` against the description (max 8 bullets); 404 unknown item, 400 `nothing_to_work_from` (no description, or a mode that changes bullets without current ones), 503 no AI. The inspector's `DescriptionBullets` (`workspace/description-bullets.tsx`) shows the buttons, the proposal with a checkbox per bullet (flagged unticked) and "Use these bullets" (ONE undo step, `batch`).

**Vault version 2: no bullets outside skills (#244).** `CURRENT_VAULT_VERSION` is 2. `foldBulletsIntoDescriptions` (`VAULT_MIGRATIONS[1]` in `shared/vault/migrate-vault.ts`) turns the bullets of every item that is not in a skills/summary section into lines of `fields.description` (after an existing description) and leaves `bullets: []`; their Short/Long/Formal wordings are dropped. A legacy file is first converted to version 1 and then goes through the chain; AI import (`importToVault`) puts points into the description too. The vault item editor and the page-level experience/education/generic editors have a Description and no bullet cards, wordings or "Add bullet" (a skills group keeps its skills list). The schema still allows `bullets` on any item and the whole bullet engine (job wording, hide, order, tailor bullet proposals, chat `hideBullet`/`rewriteBullet`, `BulletAiActions`, which is hidden for generated bullets) still works for items that have them; tests of that engine use `fixtures/sample-with-bullets.ts` (`sampleFileWithBullets`: the sample with its experience bullets) because the migrated sample has none.

**Page look (CV-39).** The default page is the UK single column (`singleColumnLayout`: header, then every section full width); `twoColumnLayout` is the older two-column look. Both are buttons on the Page Structure page (they edit the template). The preview (still MUI) draws `render(vault, {...activeVariant, layout: app.structure})`, so the preview components take `RenderedSection`, not vault sections. Date format defaults to `MMM YYYY`; the optional right-to-work line is `profile.rightToWork` shown when `style.shouldShowRightToWork`. Items use `breakInside: avoid`; the page forces black on white and `inherit` link colour so the app's global CSS does not leak in.

**Pagination (CV-40).** The preview measures itself: `usePagination` (`preview-page/use-pagination.ts`) reads the elements marked `data-cv-block` (`CvBlock`, `CvTypography pageBreak`, bullets; `data-cv-keep` = stay with the next block, e.g. headings) and feeds them to the pure `shared/layout/paginate.ts`, which pushes a block that would cross a page end to the next page and returns the page count and where pages start. The preview shows dashed `Page N` markers (hidden when printing) and a status line / warning against `pageLimit` (1 or 2, set in the page inspector or on the Jobs page, stored on the template). The same blocks carry `break-inside: avoid` for printing. `style.paperMargin` now sets the paper padding (`PAPER_MARGIN_MM`).

**Fit numbers (#88, #90).** `shared/layout/fit-metrics.ts` `computeFitMetrics` turns the measured heights into `usedPercent` and `linesOver` (line height measured from the first bullet; used height = bottom of the last block, because the paper has a one-page minimum height). `usePagination` also returns `breakLabels` (what each page starts with). `PreviewPage` stores them in `app.fit` for the top bar chip and shows the overflow banner with actions (Auto-fit, Allow 2 pages, Undo auto-fit when it cannot fit).

**Skill display (#146).** Per template `skillDisplay` (`none|dots|bars|stars`; missing = the earlier MUI rating look), `skillColumns` (1|2) and `skillMinLevel` (1-5; lower and unrated skills are left out of that template only), set from the inspector when a skills section/item is selected (`setSkillStyle`, `SkillStyleControls`). `render` puts `skillStyle` on the skills `RenderedSection` (a section that does not track levels gets `display: none`) and `SkillsPreviewPage` draws it: dots/stars as text symbols (in the PDF text layer), bars as aria-hidden drawn shapes. **Group by and skill list (#149):** `skillGroupBy` (`group` default | `level` = one flat list, highest level first, no group heading; `flattenSkills` in `render`) and `workspace/skill-list.tsx` (`SkillList`: every skill of the section with drag handle, eye, level label, up/down and a "n of m shown" count; same `setBulletSelection`/`setBulletOrders` as the item bullet list). In flat mode level order wins over manual order.

**Hide to fit (#89).** `ItemSelection.relevance` (0-100, set by `applyProposal` from the tailor proposal) ranks items; `shared/layout/hide-candidates.ts` (`rankHideCandidates`, `pickItemsToHide`) lists the least relevant first (unscored = 50, later items first, summary never) and the workspace `FitPanel` (page inspector, shown while it overflows) ticks items hidden in the job with the lines each saves, or hides the least relevant until it fits. Auto-fit itself still only changes spacing, margins and font (it does not hide). "Ask AI to pick what to hide" (shown while over the limit and AI is set up): the client sends the visible candidates (label, section, measured lines, relevance) plus the job's must-haves when the job has `tailor` to `POST /api/ai/hide` (`server/ai/pick-hide.ts`, prompt `pick-hide.md`, types `custom-types/hide-types.ts`; no profile data, short ids `c1`..., no `personal` scrubbing needed); `pickHide` drops unknown/repeated ids and stops once enough lines are saved; the panel lists the picks with reasons and only "Hide these" changes the job. Tried with llama3.1.

**Export dialog (#91).** The top bar's "Export PDF" opens `workspace/export-dialog.tsx`: it saves the job, asks the server for the real PDF (same path as before), shows it in an iframe and lists the checks from the pure `shared/export/export-checks.ts` (`exportChecks`: fits, contact details present, selectable text, no photo/DOB, hidden items; `suggestFileName`). Optional "also save JSON". **Tailor checks:** a job made from a proposal carries `tailor` (`TailorRecordSchema`: day, job title, requirements, gaps, and the flagged rewordings the user accepted by hand; built by `buildTailorRecord` when the job is created; never changes the job). The export dialog passes it and the CV's words (`shared/variant/document-text.ts` `documentText(render(...))`) to `exportChecks`, which adds "flagged rewordings still in the CV" and "must-have requirements not shown" (word match via `shared/ai/gap-coverage.ts` `isGapCoveredByCv`, the same heuristic that filters the model's gaps; it errs on the side of warning, e.g. "5+ years"). **Mark as applied after export (#138):** a checkbox "Then mark this as applied" in the dialog; after the download the same form as the top bar button (`MarkAsAppliedDialog` in `applications-page/mark-as-applied.tsx`, role prefilled from `tailor.jobTitle`) opens, and the application freezes the CV and PDF that were just exported.

**Auto-fit (CV-41).** `shared/layout/fit.ts` is a pure stepper (`startFit`, `stepFit(input, state, measuredPageCount)`, `describeFit`): `fit` mode shrinks spacing, then margins (floor 14 mm, per-template `fitLimits` editable in the page inspector; `FIT_LIMIT_RANGES`/`clampFitLimit(s)` keep them in range, the reducer clamps and an empty field is not saved as 0), then font size (body text floor 9.5 pt), then hides items from `hideCandidates` (empty until tailoring provides relevance); `fill` mode grows spacing then font size while it still fits. It never leaves the floors/ceilings. `useAutoFit` holds the state and the preview does the loop: draw with `tuning` (CSS vars `--cv-spacing`/`--cv-font-scale` on the paper, padding from `marginMm`, gaps via `spaced()`), wait until `usePagination` has measured exactly that drawing (`pagination.key === layoutKey`), step, repeat. The result is saved as the job's `tuning` (so the PDF can reproduce it); `isAutoFit`/`fitMode` belong to the template and are set on the Jobs page. Pagination/fit need a real browser to be exact; tests fake the layout.

**Drag and drop (CV-42).** Section placement (`section-placement/`) keeps its pure helpers in `section-placement-utils.ts` (`moveBetweenColumns` while dragging, `reorderInColumn` on drop) and has a keyboard sensor. Items and bullets are reordered per job on the Jobs page (`job-section-items.tsx`): a drag handle (pointer or keyboard) plus up/down buttons; the order is stored as `order` in `ItemSelection`/`BulletSelection` (`computeOrders`) and `render` applies it. Dragging is not in the preview itself.

**PDF (CV-43).** `POST /api/pdf {jobId}` (server, `pdf/pdf-renderer.ts`, behind the `PdfRenderer` interface so routes are tested with a fake) opens the web app's print-only route `/print/<jobId>` in headless Chromium via Playwright and returns the A4 PDF (text layer, background, `preferCSSPageSize`). The route is `pages/print-page/print-view.tsx`: it loads the saved vault + resolved job (`GET /api/jobs/:id/resolved`) from the API, draws `PreviewPage isPrintView` (no editor, no markers, saved job `tuning` applied instead of re-running auto-fit) and sets `@page` margin itself, so every printed page has the margin and the paper is just the text area. It signals `data-cv-ready="true"` (or `data-cv-error`) for the renderer to wait on. The PDF is of the _saved_ job, so the PDF button saves first. The old `react-to-print` Print button was removed in PR chore/remove-old-print (revert that commit to bring it back).

**AI (CV-45).** `server/ai/`: `ClaudeAiClient.generate({promptName, input, schema})` asks Claude (SDK `@anthropic-ai/sdk`, model `ANTHROPIC_MODEL`, default `claude-opus-5-5`, adaptive thinking) for a JSON object, checks it with a runtypes schema and, when wrong, sends the problem back and retries (3 attempts), else throws `AiError` (`not_configured|timeout|api_error|refused|truncated|invalid_output`). Prompts are files in `server/ai/prompts/*.md` (`loadPrompt`). The key comes from `.env` (git-ignored; copy `.env.example`), is only read on the server (`readAiConfig`), is scrubbed from every error (`redact`), and the browser only learns whether one is set (`GET /api/ai/status`). Tailoring (CV-46): `POST /api/ai/tailor {jobAd, tone}` runs `ai/tailor.ts` — call 1 extracts requirements (`extract-requirements.md`), call 2 (`propose-selection.md`) gets requirements + tone + the CV's ids/text/tags (never the profile/contact details) and returns per-item relevance/include/highlight, per-bullet include and optional rewrites (only as alternative wordings), a draft statement and the gaps; `sanitiseProposal` drops entries for ids not in the CV and clamps relevance. **Scrubbing (#81).** `shared/ai/redact-personal.ts` (`scrub`, `restore`) swaps the vault `profile` + `links` for placeholders (`[Candidate Name]`, `[First Name]`, `[Email]`, `[Phone Number]`, `[Address]`, `[Right To Work]`, `[Link n]`). `ClaudeAiClient.generate` does it for every provider when the request has `personal` (`tailor` always passes it): the sender wrapper scrubs system + all messages (retries too) and restores the raw reply before parsing; a placeholder the model changed stays and is reported through `onWarning` (shown as a tailor warning). **Undo and redo (#49, part 1).** `store/history/history.ts` `withUndo` wraps the combined reducers of the real store (`undoableReducer` in `store.ts`; the plain `rootReducer` map used by tests has no undo): after any action that makes `vault`, the templates or the jobs a different object it keeps a snapshot (vault, templates, jobs, activeJobId, action type, time) in `state.history.past` (max 100); selection, saving and other UI changes are not steps. Edits of the same action type within 700 ms (typing) are one step. `undo`/`redo` restore the snapshot and also put `app.structure` and `cvData.style` back from the active job's template (otherwise `useSyncActiveJob` would write the new layout back over the undo). `batch(label, actions)` reduces several actions as ONE step (used by the chat). `clearHistory` runs after a file is loaded (`loadCvFileIntoStore`), so undo never goes back to a previous file. Top bar Undo/Redo buttons (tooltip names the step), Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z / Ctrl+Y outside fields (`use-undo-shortcuts.ts`); undoing back to the saved state makes the Save indicator clean again because dirtiness is derived.

**Chat (#49, part 2).** Rail tool "Chat" = the canvas plus `workspace/chat-panel.tsx`. Tried with llama3.1 (CPU, ~3 min a turn): simple requests (hide an item, move a section) give valid operations; compound or ambiguous ones ("shorten my current role's first bullet and make the tone formal") made it ask a question and drop an operation, so the prompt says to use `rewriteBullet` to shorten and to give one operation per requested change; a hosted model is expected to do better. **Saving (CV-38).** `store/persistence/` (what is saved: see "Templates and jobs") holds the typed `api-client` (responses checked with the shared schemas), the pure `persistence-logic` (what changed since the last save), the slice, and `loadFromServer`/`saveToServer`. **Server** (`src/server/`): `buildServer({storage})` in `app.ts` builds the API (`/api/health`, `/api/vault`, `/api/templates`, `/api/jobs`, `/api/applications`, `/api/pdf`, the AI routes); `main.ts` only wires config and starts it on `127.0.0.1`.
