# data-model: templates and jobs, vault, bullets, saving, files, server, data repo, applications

Moved out of CLAUDE.md. Check the code before trusting a detail; file names here can lag behind.

**Templates and jobs (0.2, #165-#172).** Words: a **template** is how a CV looks (`TemplateSchema`: layout = section placement per column, style, skill display, auto-fit policy `isAutoFit`/`fitMode`/`fitLimits`); a **job** is one target (`JobSchema`: `templateId`, company/role, `selection` = hidden items/bullets, order, emphasis, wording per bullet and relevance, `tone`, `tailor` record, `tuning` = result of the last auto-fit). Many jobs can share a template, so a change of look reaches all of them; hiding and wording belong to the job and never touch the vault. The word "variant" no longer appears in the interface. **`Variant` (`custom-types/variant-types.ts`) is only the internal resolved view**: `resolveVariant(template, job)` (`shared/variant/template-job.ts`; `splitVariant` is the inverse) gives the one shape that `render`, pagination, auto-fit, the PDF and the application snapshot consume; its `id` is the job id. `render(vault, variant)` (`shared/variant/render.ts`) is the pure function that turns facts + resolved variant into the document to draw (`RenderedSection`s; sections the layout does not place go to the left column; emphasis draws the item's title bold). `Item.shouldShow` in the vault is not used.

**Item description (#242, first of three).** Experience and education items have a free-text `fields.description` (the generic type already had one; no schema change, no migration), edited in the vault item editor (`fieldSpecsFor`) and drawn by `ItemDescription` (`preview-page/item-description.tsx`: one `data-cv-block` per non-empty line) before the bullets. The bullets are made per job (#243, below); #244 removed the vault bullets.

**Bullets from the description (#243, second of three).** `ItemSelection.generated` (`{id, text}[]`, optional) holds the bullets AI made from an item's `fields.description` for that job; `jobBullets(item, selection)` (`shared/variant/render.ts`) gives the effective bullets (generated when there are some, else the vault's) and `sortBulletsByVariant`/`render` use it, so hide/order/outline/Jobs content work on them like on vault bullets (chat, tailor and hide still see the vault bullets). `generatedBulletsChange` (variant-utils) builds the `setItemSelection` change and drops choices on the replaced bullets. `POST /api/ai/bullets {itemId, mode: make|shorten|rephrase|emphasise, requirements?, focus?, current?}` (`server/ai/generate-bullets.ts`, prompt `generate-bullets.md`, types `custom-types/bullets-types.ts`, task `chat` in the provider chooser) reads the SAVED vault, sends the description + the item's other fields (never the profile; scrubbed like tailoring) and returns `{itemId, bullets: [{text, flags}]}` with `flags` always recomputed with `checkRewrite` against the description (max 8 bullets); 404 unknown item, 400 `nothing_to_work_from` (no description, or a mode that changes bullets without current ones), 503 no AI. The inspector's `DescriptionBullets` (`workspace/description-bullets.tsx`) shows the buttons, the proposal with a checkbox per bullet (flagged unticked) and "Use these bullets" (ONE undo step, `batch`).

**Vault version 3:** `CURRENT_VAULT_VERSION` is 3. `VAULT_MIGRATIONS[2]` runs `awardDatesToDays` (an award's `fields.date` is a month picker stored as a day, "Mar 2024" becomes "2024-03-01"; a bare year or other text stays as text, shown as is and as a note in the editor) and `dropSkillYears` (`Bullet.years` is gone). Display goes through `formatStoredDate`.

**References section (#464).** A new section type `references` (`SectionTypeSchema`); its items have `fields.name`, `position`, `organisation`, `relationship`, `email`, `phone` (`fieldSpecsFor`). Adding a type needs no migration and no version bump (old files do not contain it, and a file with one from a newer app is refused by `assertNotNewer`). It is drawn by `ReferencesPreviewPage`; two optional template style flags decide how: `style.shouldShowReferenceContacts` (email and phone shown; default hidden, they are other people's data) and `style.isReferencesOnRequest` (the section is the single line "Available on request"; `render` keeps the section even with no entries then). Privacy: `describeCv` leaves the whole section out of what chat and tailoring tell a model, `scoreSection` returns nothing for it, and the AI import maps a made-up `references` section to `custom`. New vaults do not start with the section; it is added with "Add a section".

**Vault version 2: no bullets outside skills (#244).** `CURRENT_VAULT_VERSION` is 2. `foldBulletsIntoDescriptions` (`VAULT_MIGRATIONS[1]` in `shared/vault/migrate-vault.ts`) turns the bullets of every item that is not in a skills/summary section into lines of `fields.description` (after an existing description) and leaves `bullets: []`; their Short/Long/Formal wordings are dropped. A legacy file is first converted to version 1 and then goes through the chain; AI import (`importToVault`) puts points into the description too. The vault item editor and the page-level experience/education/generic editors have a Description and no bullet cards, wordings or "Add bullet" (a skills group keeps its skills list). The schema still allows `bullets` on any item and the whole bullet engine (job wording, hide, order, tailor bullet proposals, chat `hideBullet`/`rewriteBullet`, `BulletAiActions`, which is hidden for generated bullets) still works for items that have them; tests of that engine use `fixtures/sample-with-bullets.ts` (`sampleFileWithBullets`: the sample with its experience bullets) because the migrated sample has none.

**Saving (CV-38).** `store/persistence/` (what is saved: see "Templates and jobs") holds the typed `api-client` (responses checked with the shared schemas), the pure `persistence-logic` (what changed since the last save), the slice, and `loadFromServer`/`saveToServer`. Nothing is saved automatically: the Save button writes what changed (vault, changed templates and jobs, deletions); `SavedState` is the text last known to be on disk. If the saved data cannot be read (`error`) or the server is down (`offline`), saving is blocked so the default empty CV never overwrites a file. Nothing is shown as a stand-in CV when nothing is saved yet (the sample CV was removed from the app; it only exists in `fixtures/` for tests). `usePersistence` (mounted in `App`) loads at start and warns before closing with unsaved changes.

**Files and migration.** The saved file is `CvFile` = `{metaData, vault, style}`. `migrateCvFile` (`store/vault/migrate-vault.ts`) reads every supported format: older legacy files (`{metaData, data, style}`) are converted, vault files go through a version chain (`VAULT_MIGRATIONS`, add a step and bump `CURRENT_VAULT_VERSION` when the format changes). Never read a CV file without it.

**Editor draft/apply pattern.** Editors edit a _local draft_ built with `useVaultDraft`: a `useReducer` over the same `vaultReducer`, so editors use the exact reducers the store uses. `useSectionDraft` adds the item operations for item-based sections. Apply/Discard/Add buttons live in the footer and communicate through the one-shot boolean flags in the `app` slice: the button sets the flag, the editor reacts in a `useEffect`, runs the callback and resets the flag. A change of the stored data (import, discard) resets the draft; visibility toggles are also written to the store at once and use `skipNextReset` so other unapplied edits survive. Editor pages are chosen by section `type` in `editor-page/editor-pages.tsx`; the preview does the same in `preview-page.tsx`. Types without a special layout (projects, certifications, publications, volunteering, custom) use the generic editor/preview (`title`, `subtitle`, `location`, dates, `description`, bullets). The Sections page (`editor-sections.tsx`) adds, renames, reorders and deletes sections and applies at once (no draft). Tags and alternative wordings are edited in `item-metadata/item-extras.tsx`, a collapsed panel that only mounts when opened (keeps the editor fast).

**Preview** (`pages/preview-page/`) reads the vault and lays parts out according to `app.structure`. Drag-and-drop of parts between columns is in `editor-page/section-placement/` using `@dnd-kit`. Typography/fonts/colors come from `custom-styles/` and `style`; shared text rendering goes through `components/cv-typography*`.

**Migrations for every file kind (#430).** Every written file has `meta` (`export-meta.ts`). The vault/CV chain is `VAULT_MIGRATIONS`; job, template, application and candidate are registered in `shared/migration/migration-chains.ts` (`MIGRATION_CHAINS`, each `{current, steps}`, empty at version 1). `upgradeFile(raw, kind)` refuses a file from a newer app (`assertNotNewer`), runs the steps and returns an `UpgradeNotice` when one ran; `describeUpgrade` makes the sentence for the user. `FileCvStorage` runs it on every load (`upgradeOnDisk`, and the same for the vault) and writes the upgraded file back through `writeJsonAtomic`, so `.bak` holds the pre-migration file. The import hook (`parseCvFileTextWithNotice`) shows the notice as an info toast and a newer-app refusal as an error toast. To change a format: bump `CURRENT_*_VERSION`, add the step, keep a fixture of the old file; `migration-guard.test.ts` fails when a step is missing.

**Import/export** (`hooks/use-import-export-json.ts`): export downloads a `CvFile`; import goes through `parseCvFileText` (which migrates). The app never starts with a sample CV; `fixtures/sample-cv.json` is for tests only.

**Server** (`src/server/`): `buildServer({storage})` in `app.ts` builds the API (`/api/health`, `/api/vault`, `/api/templates`, `/api/jobs`, `/api/applications`, `/api/pdf`, the AI routes); `main.ts` only wires config and starts it on `127.0.0.1`. All data access goes through the `CvStorage` interface (`storage/cv-storage.ts`); `FileCvStorage` keeps `vault.json`, `templates/<id>.json`, `jobs/<id>.json` and `applications/` in `DATA_DIR` (an old `variants/` is only read, see "Templates and jobs"). Rules it enforces: every read and write is validated with the shared schemas (reads of old files go through `migrateCvFile`); writes are atomic (temp file + rename) and serialised per file; the previous readable version is kept as `.bak`, an unreadable file is moved to `.corrupt-<time>` and never replaces the backup; a corrupt file is reported (HTTP 500 `corrupt`) and never treated as empty; template, job and application ids are whitelisted (`[A-Za-z0-9_-]{1,64}`) because they become file names; requests with a non-local `Host` or `Origin` are refused with 403. Templates, jobs and applications are validated with `TemplateSchema`, `JobSchema`, `ApplicationSchema`; `VersionedCvStorage` commits "Save: template x" / "Save: job x".

**Data repo (#73).** `data/` can be its own private git repo (`squeezy-cv-data`; `git clone` it as `data/`). When `DATA_DIR` has its own `.git`, `VersionedCvStorage` (`server/backup/`) wraps the storage and `BackupService` commits after every save/delete ("Save: vault", "Save: variant x"). A git failure never blocks a save; it is reported by `GET /api/backup` (`isEnabled`, `hasRemote`, `unpushedCommits`, `lastError`). Pushing is always explicit: `POST /api/backup/push` or `pnpm data:push`. A parent repo never counts (only `DATA_DIR/.git`), and without git everything works as before.

**Applications (#74).** `ApplicationSchema` (`custom-types/application-types.ts`) is one application: company, role, `appliedAt`, `status` (`applied|interview|offer|accepted|rejected|withdrawn`), a `history[]` timeline, optional job link/description/notes and `submitted` = the CV exactly as sent (`render(vault, variant)` output + the variant + tuning, deep-copied so later edits never change it). **Job and template (#171):** `jobId`, `templateId`, `jobName`, `templateName` (all optional in the file: ids and names at the time of sending, labels only, the CV itself is `submitted`). An application file from before jobs has none of them (it is still read): `summariseApplication` then uses `submitted.variant.id` as the job id and its name as the job name, with an empty template. `ApplicationSummary` has `jobId`, `templateId`, `jobName`, `templateName` (no `variantId`). `POST /api/applications {jobId, ...}` loads the saved job + template (`resolveVariant`; an old variant file already counts as a job) and records the source (`createApplication(..., source)`). Pure helpers in `shared/application/application-utils.ts` (`createApplication`, `updateApplication`, `isNoReply` = still Applied after 30 quiet days, derived never stored, `formatDay`). Stored by `CvStorage` as `applications/<id>/application.json` + `cv.pdf` (PDF written first; delete moves the folder to `<id>.deleted`). Routes: `GET/POST /api/applications`, `GET/PATCH/DELETE /api/applications/:id`, `GET .../:id/pdf`. `POST` renders the PDF of the _saved_ job and stores nothing if that fails. UI (`pages/applications-page/`): "Mark as applied" in the app bar (saves first via `hooks/save-active-job.ts`, then a dialog) and `ApplicationView` at `/applications/<id>` (status dropdown asks for a date and note, timeline, "Job: X · Template: Y", the PDF that was sent with the note that it is a frozen copy and later edits do not change it, notes, "Create new job from this" = a new job with the submitted selection on the template it was sent with (if that template still exists, otherwise the look is saved as a template of its own), delete). The Mark as applied dialog and the Export dialog title show the active job and template.

**Applications list (#75).** `/applications` (`ApplicationsPage`, linked from the app bar): one row per application (company, role, job, template, status chip, date applied; "No reply" chip derived), a summary line, a search box and status chips. The pure logic is `shared/application/application-list.ts` (`arrangeApplications` = search (company, role, job or template name) + filter + sort, `summariseApplications`, `viewToQuery`/`queryToView`). The search/filter/sort state lives in the address (`replaceState`), and the application page's back link uses `history.back()` when it came from the list, so the same search is shown again. A damaged application is shown as a warning row (never hidden by a filter) and a failed load shows the error, never an empty list.

**Personal data:** the real CV goes in `data/` (git-ignored, as is `cv-export.json`); never commit it. `data.example/` shows the layout and `fixtures/` holds fake data for tests. Older real exports are handled by the migration.

**Page limit belongs to the job.** `Job.pageLimit` (optional) is what the CV may use and what auto-fit and hiding aim for; `setPageLimit` writes it to the job. `resolveVariant` gives a job without one `DEFAULT_PAGE_LIMIT` (1); templates have no page limit. Tailoring writes the chosen limit to the new job, never to a template copy. It is edited in the right panel of Template & content, first step "General" (1 / 2 buttons plus a number 1-10, with the score-all-sections button); the overflow banner's "Change the limit" link opens that step. **Right panel design (artifact `13mt9GrnViT3842eTMv3ET`, Wizard):** `content-panel.tsx` = header ("Step n of m", step title, step select, progress segments), scrolling body, footer Back / "Next: <step>". The General step is `general-step.tsx`: a Page limit card (status chip, 1 / 2 / Custom segments (Custom is a number from 3), page drawings with where the overflow starts from `app.fit`, auto-fit switch, "Auto-fit now", "Allow n pages", "Choose items to hide" = `hide-to-fit.tsx`, which measures lines per item from the paper and hides only on "Hide selected") and one purple AI card (a provider picker per action via `ai-provider-picker.tsx`, same per-task choice as Settings, `TailorAll isEmbedded` = Score sections, "Ask AI to pick what to hide" via `api.suggestHide`, which only ticks the boxes). Purple always means AI. **Job titles scoring:** the "Header and links" step shows `job-headline.tsx` as a table of the vault's job titles (`jobTitlesOf`, `shared/vault/job-titles.ts`) with a radio to pick the one this job shows and the AI relevance of each (best first once scored; `Job.titleScores`, `setTitleScores`). They are scored through the same `POST /api/ai/score-section` with `sectionId: "job-titles"` (`scoreJobTitles`, same prompt `score-section.md`, which has a rule for "Job titles" entries; the result's `itemId` is the title text), by "Score job titles" in that card and as the first target of "Score all sections".

**Browser mode (#350, #445-#452).** The same app can run with no server and keep all data in the browser: `VITE_STORAGE_MODE=browser` (`pnpm dev:browser`, `pnpm build:browser`; `isBrowserMode()` in `web/store/persistence/browser/storage-mode.ts`). The `CvStorage` interface lives in `shared/storage/cv-storage.ts` (PDF bytes are `Uint8Array`). `IdbCvStorage` (`store/persistence/browser/idb-cv-storage.ts`, on the tiny key store `idb-kv.ts`) mirrors `FileCvStorage` with the same keys as file paths (`vault.json`, `templates/<id>.json`, ..., `applications/<id>/application.json`), the same schema checks and migration chains, `<key>.bak` for the previous version and `<key>.deleted` for deletes. `createLocalFetch(storage)` (`local-api.ts`) answers the storage routes (same addresses, bodies and error codes as `server/app.ts`) and is the default `fetch` of `createApiClient` in browser mode (`apiFetch`); keep the two in step when a route changes. The AI routes are shared: `server/ai/ai-routes.ts` (`createAiRoutes`) is used by Fastify and by the browser (`browser/ai/browser-ai.ts`: the user's own keys in localStorage, never in a backup; `vite.config.ts` swaps `@server/ai/prompts` for `browser-prompts.ts`, prompts bundled as text). PDFs: the Export dialog previews `/print/<job>` and uses the browser's print ("Save as PDF"); an application keeps its frozen data only, and `/print-application/<id>` draws it again (`PrintApplicationView`; `applicationPdfUrl` returns that address in browser mode). Full backup: `shared/backup/full-backup.ts` (`GET`/`POST /api/backup/file`, "Your data" dialog), the way to move data between browsers and from server mode. The PWA (manifest, service worker, `registerType: "prompt"`) exists only in the browser build. Hosting: `docs/hosting.md` (Cloudflare Pages, the address must not change). Not available in browser mode: reading a PDF to import (`/api/import/pdf` answers 501 `browser_unavailable`), the feedback route and git backup.
